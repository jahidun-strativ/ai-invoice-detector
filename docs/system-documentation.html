1. System overview

AI Receipt Scanner digitises paper expense receipts for a Strativ office. It runs entirely on staff phones, calls one external AI service to read each receipt, optionally mirrors the results to a shared database so the team sees one another's scans, and produces a monthly Excel Bill Approval Sheet for sign-off.

It is not a server-side system. There is no backend to operate, no cron, no queue, and no admin panel. The operational surface is: the app on each phone, one AI vendor account, and one Supabase project.

Design principles

PrincipleConsequence
Local-firstSQLite is authoritative. The app is fully usable with no connectivity except during the AI call itself.
Failure must not cost dataSync is fire-and-forget and retried. A sync failure is never presented as a failed scan.
Additive sync onlyThe pull adds and refreshes; it never deletes local rows. There is no delete permission on the remote at all.
Monthly deliverableThe output is one signed document per month, not a live feed.

2. Components

ComponentResponsibilityFailure behaviour
Quality gate
utils/image-quality.ts		 Rejects blurry, dark or non-receipt photos on-device before any API call. Runs on a 160 px thumbnail. If it cannot analyse the image it passes the photo through rather than blocking the user. Staff can always override.
AI client
services/ai-vision.ts		 Sends the compressed image to OpenRouter, receives structured JSON, normalises it. Never throws. Returns an error object the capture screen renders. Retries with backoff; aborts immediately on 401/402.
Local store
services/storage.ts		 SQLite: receipts, config, export columns. Statistics and month queries. Retries a stale connection (a known Android execAsync null-pointer condition) by reopening the database.
Sync client
services/remote-db.ts		 Pushes rows and photos to Supabase, pulls the office's rows back. Silent and non-fatal. Unsent receipts stay marked pending and go on the next app launch.
Sheet generator
services/xlsx-export.ts		 Builds the Bill Approval Sheet from a month's receipts and the column config. Purely local and deterministic. No network dependency.
OTA client
hooks/use-ota-updates.ts		 Checks for a JavaScript update 3 s after launch; manual check in Settings. Silent on failure; the installed bundle keeps running. Disabled in dev builds.

3. Data model

On device — SQLite

Database receipts.db, three tables.

ColumnTypeNotes
idTEXT PKreceipt_<timestamp>_<random>. Generated on device; also the remote primary key.
merchant_nameTEXTNullable. May hold Bangla text.
receipt_dateTEXTISO YYYY-MM-DD, or null when unreadable.
receipt_numberTEXTNullable.
invoice_typeTEXTretail, restaurant, utility, service, unknown.
itemsTEXTJSON array of line items.
subtotal, taxREALNullable.
totalREAL NOT NULLRequired — a receipt with no total is not accepted.
currencyTEXTDefaults to BDT.
payment_methodTEXTNullable.
confidence_scoreREAL0–1, recalibrated against field completeness and arithmetic consistency.
image_uriTEXT NOT NULLfile:// = scanned on this device. An https:// bucket URL = pulled from the database. Empty = pulled, photo unavailable.
raw_text, error_messageTEXTDiagnostics.
created_atTEXT NOT NULLISO timestamp.
synced_atTEXTNull means not yet in the shared database. This single column drives all offline catch-up.

config stores key/value settings (office name, optional endpoint). export_columns stores which sheet columns are enabled and in what order. Indexes exist on created_at, invoice_type, merchant_name and substr(receipt_date,1,7) for month queries.

Why receipt_date can be null Handwritten receipts sometimes have no legible date. Month queries use COALESCE so those receipts appear in the month they were scanned rather than falling out of every month's sheet — which is what happened before, and meant expenses silently disappeared.

Shared — Supabase

Defined and re-runnable in supabase/schema.sql.

ObjectPurpose
receipts tableMirrors the device columns, plus office_name (one project can serve several offices) and image_path (object path of the photo). Upserted on id.
receipt-images bucketPrivate. One object per receipt, <receipt id>.jpg, 5 MB per-file limit.

Row-level security is enabled and the app holds the anon role only:

Operationreceipts tablereceipt-images bucket
insertAllowedAllowed
updateAllowed (needed for upsert)Allowed (needed for replace-on-reupload)
selectAllowed — this is what makes the team view workAllowed
deleteNo policyNo policy

The missing delete policy is the single most important line in the schema: a leaked key cannot erase the office's expense records. Deletion requires the Supabase dashboard or the service key, neither of which is on any phone.

4. Synchronisation

Push

  1. A receipt is saved locally with synced_at null.
  2. The photo is resized (1600 px, quality 0.7) and uploaded to the bucket; the returned object path goes on the row.
  3. The row is upserted on id with resolution=merge-duplicates, so re-sending never duplicates.
  4. Only ids the endpoint actually accepted get synced_at stamped. Everything else is retried on the next launch.

Editing a receipt clears synced_at, so corrections propagate. A photo that fails to upload does not hold back its row — the record syncs with no photo, and Settings → Data → Re-upload all receipts sends it later.

Pull

On app start the device fetches the office's receipts (newest first, 2000-row limit) and merges them. The ownership rule decides each row:

Local stateAction
Row absentInsert it. Another phone's scan appears here.
Row present, image_uri starts file://Skip. This device scanned it and owns it.
Row present, came from the databaseRefresh it, so a correction made on the owning phone arrives.
Never delete local rows to match the remote An empty read is indistinguishable from a blocked, rate-limited or failed one. "The table looks empty, so clear the phone" would destroy the office's records, including scans that had not uploaded yet. If the remote table is emptied by accident, recover the other direction: Settings → Data → Re-upload all receipts clears synced_at and pushes everything back.

Consequences to be aware of

  • Sync is eventual. Two phones agree after both have opened the app with a connection, not immediately.
  • There is no conflict resolution. If the same receipt is edited on two phones, the last push wins. In practice one person owns a receipt, so this has not occurred.
  • Photos load over the network on the phones that did not take them, so the History list on those devices needs a connection to show thumbnails.
  • Running without Supabase configured is fully supported. The app is then single-device and every sheet covers one phone's scans.

6. Security model

What is exposed

Every EXPO_PUBLIC_* value is compiled into the JavaScript bundle. Anyone who obtains the APK can extract the OpenRouter key and the Supabase anon key. This is inherent to a client-only app with no login, and is accepted for internal distribution. The mitigations are structural rather than secret-based:

RiskMitigation
Extracted OpenRouter key used to spend moneySpend cap on the key. Rotate via MAINTENANCE.md §3 — a rotation is an OTA update, not a rebuild.
Extracted anon key used to read expense dataAccepted. The data is internal merchant names, dates and amounts. Add Supabase Auth if that changes.
Extracted anon key used to destroy dataNot possible. No delete policy exists on the table or the bucket.
Receipt photos read by an outsiderThe bucket is private; reads require the key. Public URLs were rejected because receipt ids embed a timestamp and would be partly guessable.
Lost or stolen phoneReceipts already synced are safe in the shared database. Unsynced scans on that device are lost. There is no remote wipe.

Data handling

  • Receipt images are sent to OpenRouter for extraction. Treat that as processing by a third party when assessing what may be photographed.
  • Photos are stored twice: on the capturing device and in the private bucket.
  • The app collects no personal data about its users — no accounts, no analytics, no tracking.
  • Android permissions requested: camera, and read/write external storage for importing and sharing files.

VariableWhere it is setEffect if missing

EXPO_PUBLIC_SUPABASE_URLSameApp runs local-only; no team view.
EXPO_PUBLIC_SUPABASE_ANON_KEYSameIf the URL is set but the key is not, every sync is rejected. The app logs a warning at start.

The database endpoint is build configuration, not a user setting. There is deliberately no field, status indicator or sync button in the app: a phone is pointed at the office project by installing the build, and nothing else. Staff have no reason to see a database URL, and every extra field is another way to break sync.

8. Build, release and update

Which mechanism applies

ChangeMechanism
JavaScript, TypeScript, styling, prompt, sheet layoutOTA update. Reaches phones on next launch.
API key rotationOTA update (the key is read from the bundle).
New native module or config plugin, app.json native change, SDK upgradeNew build. Each phone reinstalls the APK.
Database columnSQL first, then OTA. See the warning below.
 
# Ship a JavaScript change to the phones staff use
eas update --channel main --environment preview -p android -m "what changed"

# Build a new APK when native code changed
eas build --platform android --profile preview
Order matters for schema changes Apply supabase/schema.sql before publishing an update that references a new column. PostgREST rejects a payload naming an unknown column, so the wrong order does not degrade sync — it stops it completely, for every device, until the SQL is run.

An OTA update only reaches builds with a matching runtime version, and the policy is fingerprint — the runtime version is derived from the app's native dependencies rather than its version number. An update is therefore only ever offered to builds with the same native shell, and a rebuild is required whenever those dependencies change. Exact procedures: MAINTENANCE.md §1 and §2.

Why the policy is not appVersion It was, until the SDK 57 upgrade. Under appVersion the runtime version is the version string, so an SDK 54 build and an SDK 57 build both claimed 1.0.0 and sat on channel main together — one OTA would have been served to both populations, and a bundle built against React Native 0.86 crashes on launch inside an 0.81 shell. Nothing warned about it; the versions simply matched. fingerprint makes that combination impossible rather than merely discouraged.

9. Operations

The monthly cycle

  1. Staff scan receipts as they arrive, throughout the month. No network needed beyond the scan itself.
  2. Corrections are made on the phone that scanned the receipt, via the detail screen.
  3. At month end, one person opens Export, picks the month, enters the amount received from the account and the four signature names, and generates the sheet.
  4. The sheet is shared from the phone (email, chat, or file share) and printed for signature.

Before generating, confirm every phone has opened the app with a connection — otherwise a colleague's unsynced scans will be missing from the sheet.

Runbook

SymptomCause and action
"OpenRouter API key not found"Key missing from the build, or the dev server started before the variable existed. Restart with pnpm start --clear; for a build, check the EAS environment variable and publish an update.
Scans fail with 402OpenRouter credits exhausted. Top up or rotate the key (MAINTENANCE.md §3).
Scans fail with 401Invalid or revoked key. The app stops retrying immediately by design.
A colleague's receipts are missingTheir phone has not synced. Have them open the app with a connection; the backlog uploads automatically. If it persists, check the Supabase URL and anon key are both present in the build.
Photos show as blank thumbnailsExpected for receipts scanned before photo sync existed, and for any upload that failed. Settings → Data → Re-upload all receipts on the owning phone backfills them.
Nothing syncs at all, from any deviceAlmost always a schema mismatch — an app update shipped ahead of its SQL. Apply supabase/schema.sql.
Remote table was emptied by accidentDo not clear any phone. Run Settings → Data → Re-upload all receipts on each device.
Bangla text is unreadable in an exportConfirm the file is .xlsx. CSV cannot carry the encoding reliably and was removed for this reason.
Blurry photos being acceptedThe quality gate is threshold-based and can be recalibrated in utils/image-quality.ts. Constants are at the top of the file.
App will not open after an updateReinstall the APK. The previous OTA bundle is replaced, not kept, so rollback means publishing a corrected update.

10. Known limitations

  • Eventual consistency, no conflict resolution. Simultaneous edits on two phones resolve last-write-wins.
  • No authentication. Possession of the app is possession of the office's expense data.
  • No remote wipe for a lost device, and unsynced scans on it are unrecoverable.
  • No backup automation. Supabase's own backups are the only copy beyond the phones. Nothing exports the table on a schedule.
  • Delete-all is available in Settings and is protected only by a two-tap confirmation. Consider hiding it before wider rollout.
  • iOS is configured but untested. Bundle identifier and permissions exist; no iOS build has been distributed.
  • Accuracy is not guaranteed. Confidence is reported per receipt and low-confidence scans are flagged, but a human check before approval remains part of the process. That is what the signature blocks are for.
